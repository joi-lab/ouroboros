# 12. Host Service, Companion Processes, and Chat IDs

Reviewed-skill ingress, Presence, companions and chat-id delivery live here. Chat ids are values, including the hidden destination; reviewed owner-bound transports are control surfaces. External speech remains observation with provenance, never an owner request; unknown outcomes never authorize another attempt.

### Host Service boundary

The Host Service (`ouroboros/gateway/host_service.py`, port `OUROBOROS_HOST_SERVICE_PORT`) authenticates every request with an opaque `x-skill-token` bound to payload hash, executable review, enablement and grants; tokens hold no secrets, go stale on a payload edit and refuse stringification (`skill_token.py`). Routes and permissions: the §4 table's Host Service rows. `POST /notify` (`host_notify.py`, grant `notify_owner`, advertised as `notify_version` on `/identity`) writes one sentence of at most `NOTIFY_TEXT_MAX_CHARS` as a `skill_notice` System row in the owner's chat signed `Notice · <skill>`, waking no model; 503 means the row is unconfirmed. Transport review covers identity and attribution, bounded polling, panic cleanup, token confinement and exfiltration. An owner-bound reviewed transport can control Ouroboros; external slash commands bind a separate positive-identity owner slot (`supervisor/state.py`), so an unidentified transport cannot bind and web identity cannot lock out the remote owner. `wait_for_response` is A2A-only.

Shared decision and language writers: §4 Server API Endpoints. Review-operation waits reach their exact live controller after author completion through the canonical `pending_action`; a stale revision or identity, or no consumer, is 409 (§6 Quota and auth waits). A review verdict grants no continuation or additional skill authority.

Admission is one limiter with two policies (`host_service._RateLimiter`): the WS relay lane (`/ui/ws-message`) is a token bucket, so a burst does not silence a widget for the rest of a minute, and every other lane keeps the sliding window. Refused relays aggregate per burst into one durable `host_service_ws_relay_dropped` row in `logs/events.jsonl` with the dropped count; the child's `send_ws_message` stays best-effort `None`, and the in-process broadcast path has no bound.

Chat uploads have one storage owner, `chat_uploads.store_upload`, for Host-confined paths and completed multipart spools: the Host Service calls it directly, the browser's `/api/chat/upload` through the `gateway.files` facade. The request's worker both copies and closes its spool, so HTTP cancellation cannot interrupt cleanup; the skill keeps its source. Neither ingress rejects a file for its size; the Host's request count bound (`_INJECT_ATTACHMENT_MAX`) and the Files-browser upload policy keep their own contracts. Host attachment copies share one request-local cleanup stack: a partial copy, refusal or cancellation removes only new unaccepted copies, a replay never adopts duplicates, and accepted bytes survive disconnects and unknown write outcomes, which claim no acceptance.

### Operation correlation

A named injected message has `operation_ref=<chat_id>:<client_message_id>` on 202, 200, 504 and disconnect responses. `supervisor.message_ingress.accept_local_message` accepts a named message and raw `reply_to`; host resolution precedes the canonical row, and work queues only behind a landed `log_chat` row. A repeated same-id, same-text, same-skill delivery rejoins even before supervisor dequeue; changed content, source or Reply address is refused with 409. Content includes the ordered `[sha256, name]` of the inline photo and files (`chat_uploads.same_message`): a regenerated stored name is the same message. The inline photo (`_INLINE_IMAGE_MAX`, judged before decode; wire rules: CREATING_SKILLS `inject_chat`) is parked once in `data/uploads` and always staged, so model pixels keep a retained original; bytes that prove no image stage as an ordinary file, never vision under the transport's label. The queue stays in memory: a crash after acceptance can lose delivery and reads `lost`, never authorizing a second enqueue; one same-id retry of a canonical write that raised in this process hands the row over (`queued`). Routing annotations and outbound task ids are discovery hints only: task reads and cancellation require the queue or task record's complete `origin_message_ref` to match the authenticated skill's canonical source (`DirectActivityRegistry` carries the same origin); a named response wait polls that exact operation and its retry-aware effective result; chat ordering never proves a reply. Cancel enters the durable intent and cascade-custody owner (§5) only for work with that origin and the same installation root; anything else is `cancel_unsupported` before any intent is written; unresolved custody never becomes a false `cancelled`.

### Focus in places

`POST /presence/turn` (`presence_runner.py`) admits exact provider, account, conversation and thread facts, skill-confined files and an authenticated place; conversation and active-turn gates hold cross-process leases, and an HTTP disconnect neither cancels work nor returns capacity early (only a continuing author's yield does). The Host joins a live retry by turn ID only when the canonical conversation, actor and text match; a mismatch is `presence_event_identity_conflict` (409, rejected), never another room's answer. Refusal codes and dispositions on the wire: CREATING_SKILLS "Places and focus transport ingress".

A turn never acts twice on an unknown outcome. Before effects, `handle_task` writes and reads back its source-bound RUNNING row naming its controller; ambiguous writes remain retryable without regeneration authority. A lost stack, unknown terminal or cancellation returns a retained refusal: the transport keeps the event and receipt, releases its input FIFO and observes the original and any actual child separately. `/presence/work` stays `pending` while the attempt can change (`presence_recovery.attempt_ended`), then serves the canonical answer, or `failed`/`cancelled` with `outcome: silent` (nothing more to deliver) and the unknown as facts; released outputs keep their identities; the orphan sweep settles the row `failed`/`presence_attempt_lost`. `presence_recovery.py` records `host_task_facts` for room memory and ordinary consciousness, with no forced owner question or correspondent apology. Missing evidence proves neither silence nor no effect.

A quota refusal permits event regeneration only with `presence_retry_proof`: a first-round temporary refusal whose routes were engine-confirmed `not_started` and ledger-released, with no response, tool or handoff and a dated reset. After that reset the conversation gate writes `presence_retry_next`, a new physical ID addressed through the original event. Otherwise the refusal is retained. Pure-model recovery inside a running turn uses shared configured fallback/continuation (§6), retaining earlier tools and unknown cost. The live turn keeps its conversation under existing controls until recovery finishes or returns a retained refusal; it never replays the event.

Same-author continuation (`presence_continuation.py`): an author waiting for a review it left for an addressed message (a commit, change or result review, `review_pause`) keeps its stack, task, controls and paid review but lends its conversation. At the review park, only with its own tool, process and service custody idle, it persists and reads back a source-bound write-once initial envelope on its RUNNING row, lists itself in the conversation's `open_turns`, publishes the envelope, then lends conversation and active slot; before any further model, tool or forced call it reacquires both in admission order and reads the `[PRESENCE CONVERSATION RESUMED]` facts since its yield. A hard stop meanwhile ends on the zero-call control rail; rounds and wallet are not reset. Only a `continuation_version: 1` consumer takes the initial envelope, and a review verdict publishes nothing itself. A released selection (`output_ref`) is never resent; without `continuation_version` the request waits for the author's terminal. Once its attempt ends, the next turn sees the author `interrupted`; no author restarts automatically, and an explicit new event continues from retained facts as a new turn. Wire shape: CREATING_SKILLS "Presence continuation".

Reentry keeps the exact observed rows and read gaps in an immutable `presence_reentry` checkpoint in the existing task artifact store, read through the caller's existing task-read scope (`get_task_result(task_id, presence_reentry_sha256, …)`, paged by `presence_reentry_offset`); no reader or capability is added at reentry. Reads probe the producer's conversation chat id in `state/dialog.sqlite` within frozen byte bounds; legacy cursors resolve through the import ledger, new snapshots bind their end to a retained row identity, and a pre-cutover snapshot holding only inode/mtime witnesses reports `legacy_source_identity_unavailable` with its retained text still readable. Import gaps stay explicit, never empty-complete (§6 Durable memory and project focus). Transport inbox observations (`presence_observations.py`; `event.conversation.transport_queue` or authenticated `POST /presence/work/{continuation_ref}`) are dated observations of queued events, never inbox certainty, admission or delivery proof; no received snapshot means unknown.

Entry and receipts key on `presence_bindings.conversation_key` (empty thread `0`). The durable `first_lent_at` anchors later parks and terminal writes, so a returning author updates its own open entry without replacing a newer turn's pointer; `open_turns` retains each unfinished author independently. Outcomes are `message`, `silent`, `tool_delivered` and `deferred`; deferred requires admission, and orphaned children replay silent. `peer_roster.independent_message_target` admits `forward_to_worker` to a source-bound RUNNING turn as peer context, not an owner directive. Proactive speech uses connector tools.

`places.py` owns the revisioned, atomically edited `state/places.json`. A one-time migration copies legacy bindings and behavior instructions, topics, model and folder without deleting source files or changing origin/destination identity. `ouroboros/gateway/places_api.py` and `configure_presence` share its writer; only an owner-door turn or authenticated owner API can confirm an owner account. A connector update cannot overwrite owner or mind choices.

`ouroboros/gateway/host_service_places.py` captures each source event and attachments before wake, allowance or capacity decisions. Paused, Off/Panic and unmatched events settle as heard/silent without model work. Exhausted or unknown allowance asks the transport to retry. `conversation_lease.py` owns the existing process and file locks, lending and reacquisition; a live author receives `place_event` context-only mail only while its intake is accepting under the same local admission lock used by its final drain and a held conversation lease. A closed, ended or remote author leaves ordinary focus admission eligible; a final drain that accepted new place context gives that author a round to consider it without changing owner authority. Stop sees lent authors in other processes through their held stack-lifetime locks too. Reentry checks `supervisor.consciousness_carriers.autonomous_work_enabled` before reacquiring and uses the ordinary zero-call control rail when disabled. The focus has consciousness provenance, autonomy and a root cost ceiling, with no new capability ceiling; old stored ceilings remain decodable.

`presence_context.py` places `prompts/FOCUS.md` at the user tail after the shared prefix, with host actor facts, matched authored wakes, authored notes, existing work, allowance, roots and the folder address. Full knowledge topics remain context. `finish_task` selects an answer or silence. `place_reply.py` checks current place state and calls Safety with `place_reply` before automatic speech: flags return to the mind, Silent/Paused/disconnected and Advises holds become System rows, and late delivery receipts remain evidence with a visible warning. The retained place/destination carrier selects this boundary for promoted roots too, without a wake stamp. Cached turns, continuation envelopes and work polls recheck current place state without generation or another Safety check; silence is an outward projection that preserves the durable answer and output identity. One notice per task and reply subject records a hold. A forced final that cannot return a flag to the mind is held. Transport custody, receipts, continued outputs and recovered work keep their existing identities.

Receipt reporting is negotiated per turn (wire fields: CREATING_SKILLS "Reporting actual Presence delivery"); `presence_delivery.py` accepts authenticated `POST /presence/delivery` observations through the chat writer. Mode 1 writes outgoing history on provider receipts; mode 0 keeps an authored, delivery-unconfirmed row. Speech is typed `presence_delivery`, never a task-finalizing untyped row; failed or uncertain attempts are System facts. Receipts prove writing, not reading: identical readable reports deduplicate, conflicting ones refuse, and a malformed retained row makes the projection `history_coverage=gapped`, where `duplicate=false` means only that no matching readable receipt was indexed. Transport outboxes own provider receipts and their report backoff; a slow or failed report neither resends nor blocks delivery. Lookup is by the receipt's deterministic client id in `state/dialog.sqlite`, Host restarts included, and is refused while import coverage is unknown.

### Companion processes

Companion processes are host-supervised: reviewed manifest-declared descriptors enter durable custody, reconcile after lifecycle changes and restart, and stop on disable, unload or panic. `state/extension_generation.json` carries the opposite direction, the server's published live set, which a running task worker adopts at a task's start or at a dispatch miss, so an enable after boot is not invisible until the pool respawns. Worker-side changes write durable reconcile requests (`state/extension_reconcile/`) rather than spawning server-owned children, and every reconcile state names the process that answered. Health is process-qualified: aggregate and Skills UI health take the server observation as authority and expose the worker observation only as a qualifier, so a failed handoff cannot advance `last_known_good`; restart-budget exhaustion persists a terminal reason cleared only by a later successful start. A companion's cwd is the reviewed payload directory, so a payload edit stales review before reload instead of silently mutating a live process. The live projection is `state/extension_companions.json`.

### Chat-id delivery

Each message has exactly ONE destination. Chat IDs are values; absence is `None` (§11.1 `chat_id_policy`). `HIDDEN_CHAT_ID` (0) is the real hidden destination for Skill Review and unbound headless work, with no browser reader. `message_bus.notification_chat_route` decides where a notice goes; a `chat_id=0` history query coerces to Main, excluding chat-0 rows. A lineage binding or the task's admitted Project chat brings them to a Project; negative A2A ids never enter human streams. An exhausted terminal outbox notice skips chat 0 (no reader) while the durable incident and saved message remain; only positive same-id, same-destination evidence suppresses that notice (`terminal_delivery`), never a bare delivered id or a missing ACK. Memory and consolidation provenance follows the same value/`None` policy: a per-window registry snapshot names Main and the current Projects with stable chat ids, missing or ambiguous values stay explicit and never default to Main, and a presence room is named only by transport facts that re-derive its chat id. These labels are read-only source attribution and alter no routing, visibility or delivery state.

The place implementation is split by responsibility: `places_migration.py` reads legacy inputs once; `place_intake.py` decides attention after capture; `place_arrivals.py` stores heard-only decisions in existing room dedup records, defers source blobs until focus admission, and reads room/activity indexes; `place_projection.py` builds owner summaries; `ouroboros/gateway/places_api.py` writes owner choices; `ouroboros/gateway/host_service_places.py` serves connector intake, lookup and receipts. `loop_completion_schema.py` selects the available completion entry, preserving an already-live legacy registry. The declared-effect and target checks come from `tool_effects.py` and `place_guard.py` (§13).

Heard-only events leave no task document or context-source blob. Their existing accepted room row retains the event identity and a final attention reason (`paused`, `off`, `no_wake_match`, or current-author handoff); a later On does not reconsider a retry. Focus start and heard settlement share the intake lock, so an admitted task keeps its original custody. The immutable source row is never rewritten; `dialogue_store` projects the deferred focus-source pointer from its existing dedup record; `chat_chain.source_row_id` keeps the original source identity for that typed reader projection.

The Places view uses indexed newest-arrival seeks and a SQL aggregate of nonterminal focus facts, with no historical arrival walk or per-arrival document load. `places.place_room_index` returns captured room addresses and nullable unanswered counts; absent task-store knowledge stays unknown. The SQLite indexes build once and remain derived from their original rows. `account_candidates` suggests at most 20 people from the newest 50 indexed arrivals, omitting bots; these suggestions neither confirm identity nor retain a second actor list. Partial legacy migration records each bad binding in `migration.problems`, imports valid neighbors, and publishes the marker once. `GET /api/places` exposes `migration_problems`.

For an opaque outbox mutation (empty conversation id), `GET /presence/place` reports any Silent/Paused place owned by that authenticated connector/provider/account, including broad and migrated wildcard accounts. An optional `thread_id` resolves a topic-specific place; omission keeps the room lookup. Declared tool destinations match account, conversation and thread as separate facts, and each recipient is checked independently. Retained-work GET/POST may omit `binding_id`; authentication checks the retained task's connector, never the ref alone. POST accepts exactly `transport_queue` plus an optional `binding_id`; legacy binding ids remain checked.
