# 13. External Skills Layer

Built-in and installed payloads, dependencies, staging and Telegram. Discovery, review, grants, dependency readiness and enablement stay separate facts because collapsing any two turns a UI toggle into execution authority. Granted context snapshots reuse §6; protocol: `CREATING_SKILLS.md`.

### Skill gates

Discovery is not trust; review/ON prove no readiness. Payload/state paths: §1. Install → preflight → digest-bound review or acceptance → grants → dependencies → enablement → execution; extensions need registration (§10 invariant 8). An enabled peer's conflict applies symmetrically. One queue (`skill_lifecycle_queue.py`) owns mutations. `answer_or_job` awaits completion unless the client requests early job replies; older UI and dictation stay terminal. Enable survives a grant in the same job; grant and setup results stay separate (CLIENT_CONTRACT §11). Panels lend the lane and persist only for installed bytes. Full reviews stay private; UI labels dead-process/stale-heartbeat jobs interrupted without writes. List reads heal nothing. Ordinals (allocated under the lifecycle lock after job start) are display facts, never review authority.

A state read shares one location inventory between canonical identity and fresh manifest/enablement peers (`skill_peer_inventory.py`); only the selected payload is hashed. Tool enumeration shares each skill's verdict under the existing registry lock, never across requests. Lifecycle and dispatch rechecks stay: disable, revoke and restored-mtime edits apply next request. Both readers use `skill_loader._native_platform_visible`: foreign built-ins stay hidden except retained Windows Unix-remote copies (§2); OFF preserves provenance, not execution authority. `skill_conflicts.py` keeps the symmetric verdict aligned; unreadable payloads do not erase valid conflicts.

### Skill review authority

A reviewer's configured rights separately govern checks of untrusted code in its private copy: Full is not an OS sandbox, and checking grants no skill activation.

Skill review is one subject of the one review machinery: `skill_review` (`skill_review.py`) freezes the payload at its loader hash and runs `review_change(subject="skill")` (`tools/review_skill.py`); the wave's `surface="skill"` ledger record is what `review.json` projects. Seats answer the one skill question (findings only) over the checklist and the skill governance layer; the checklist's severity policy decides what blocks; a re-review is change-focused in every mode; the ceiling counts `review_skill` rows per root task or, manually, per content version.

Preflight failure persists as PENDING, never advisory-overridable BLOCKERS. Records bind the release digest (`skill_identity.py`: payload plus dependency declarations, without install notes); conversion rebinds only proven unchanged bytes. Host facts admit exact bytes without a panel: trusted source, `self_check` (Cyber Pro only), owner Skip, or owner edit by the owner's selected-skill task. In ordinary tasks, owner-requested edits use `skill_owner_action` Skip with `owner_source` carrying the owner's words. Edits invalidate earlier acceptance. Review-source blockers stay off under Advisory, author finish included. Elsewhere Advisory author finish accepts after substantive feedback or the exact reference of a terminal review that formed no verdict; it runs preflight and records `author_disposition.review_reference`. A running review is not unavailable. `SkillReviewState.gate_for` supplies one authority without rewriting critic facts; Blocking needs fresh approval, Cyber keeps P0/P3 judgment. Publication: §6.

### Telegram built-in

The thoughts menu and completion notifier read bounded chat/progress windows from `state/dialog.sqlite` (legacy log paths are addresses only); an unavailable window (import, failed segment, invalid interval) never initializes or advances notification seen IDs, and thoughts keep their preview limits.

`skills/telegram/` owns the in-process bridge and supervised companion (sidecar/tunnel/menu rollback/heartbeat/singleton). Text needs no tunnel. The built-in (`skill_builtin.py`) needs grants; Colab waits for its executable install, auto-grants eligible items when the owner allows, then enables. `data/state/skills/telegram/` keeps binding, companion, rollback, cursors, tunnel cache and bounded derived message references; map write faults warn, never stop delivery. Confined files enter `/chat/inject` then `data/uploads`; quiz answers use `/chat/decision`. Other replies carry row/work facts, never routing; status notices reference work, not Main's unseen answer. Earlier same-chat owner messages get native replies. Continue messages stay separate; relay success is silent, failure one line. Oversized files point in-app or to an active Mini App; no tunnel starts, no URL is published. `lib/telegram_i18n.py` uses `OUROBOROS_UI_LANGUAGE` (§7), preserving host lines; `/language` uses Host `/ui/language`. The completion toggle gates terminal/Main status notices; Off consumes IDs. Replay enriches `completion_notice` (§3), not text. Silent Mode, replies/files/quizzes and salvage stay independent; events only wake one `TypingCue` over `ouroboros/gateway/reply_preparation.py` (DESIGN §9). `TELEGRAM_PROXY` covers Telegram API only, otherwise egress is direct; dependency locked `httpx[socks]`. Limits/proxy forms: `skills/telegram/SKILL.md`.

`skill_catalogue.py`: `list_skills` pages whole compact records, including disabled, unreviewed, broken and colliding skills, with counted omissions. Snapshots track membership only; pages are not atomic. Named reads give full diagnostics and `manifest.read` for the loader-selected `SKILL.md` or `skill.json`; bodies stay there. Unreadable payloads never hide readable manifests; unparsed/colliding ones have no address. Unknown names return `found: false`; oversized details use the generic result source. `model_experience` reaches bounded context; `SkillManifestError` carries `fix_hint`. Delegate index: §6.

### Sources, installs and dependencies

`skill_sources.py` owns the source list. Defaults until chosen: Official trusted, Community review; trust changes affect future installs. Git caches in `state/skill_sources/` read github.com HTTPS without the configured GitHub token, then retry authentication refusals once with it alone. Other URLs use host credentials. Hubs provide entries, digest endorsements and categories; plain repos, manifest folders. `skill_source_install.py` verifies releases and records basis. Ouroboros uses `check: review` (panel); only in Cyber Pro may it pick `self` (reads the exact release, records why); trusted sources skip it. HTTP: `ouroboros/gateway/skill_source_contracts.py`.

Updates compare candidate and optional local digests. Replace keeps `.previous`; keep skips; merge uses the owner's task door. Review-basis updates retain payload and lifecycle state; `pending_update` names the candidate. Completion, owner Skip and background startup settle in the lane: accept executable bytes or restore and reconcile, recording `update_rejected` for review, preflight or landing/dependency failure. Startup leaves live reviews alone. The pre-update record restores an interrupted landing; superseded installs discard snapshots. Partial restores keep evidence and never replace payload twice. Update without review binds `owner_skip` to the exact release. Starters accept any source; absent/blank selects defaults, `[]` none. `OUROBOROS_STARTER_SKILLS_TURN_ON` defaults true (§7); built-ins precede git fetches.

ClawHub archives land atomically with per-file hashes. `skill_dependencies.ensure_skill_dependencies`, gated by what admits the bytes, readies packages for every runnable request; `removal_action` names each skill's removal. Accepted declarations authorize literal build/check argv (`marketplace/install_specs.py`); manual instructions stay guidance. Caches: `state/skills/<name>/dependency_cache`; results: `deps.json`; absent checks stay unknown and drift invalidates readiness. `provenance.py` clears only the local receipt. Script runtimes: `tools/skill_exec.py`, `docs/CREATING_SKILLS.md`.

### Extension import and isolation

Extensions share complete staged trees under `__extension_imports/`, addressed by content hash and runtime/dependency identity, reference-counted per process and reclaimed only when unreferenced with dead owners (`_stage_extension_import_tree`, `extension_import_staging.py`); review/grants stay bound to code. Per-call child processes may proxy tools, routes, WS, UI, settings and companion descriptors, while persistent subscriptions and supervised tasks need in-process or companion lifecycle; the capability matrix reports which, never a platform name. Isolated children reuse that staged loader with a scrubbed env. `extension_catalog.json` caches a successful catalog only for a manifest declaring its exhaustive `catalog_inputs` (settings and environment keys; the key hashes runtime, host revision, grants and the declared values, never persisting them); registration that depends on anything else keeps its catalog child, and no bundled payload is implicitly opted in (`extension_import_staging.declared_catalog_inputs`). In-process extensions are the powerful path, so namespacing, declared permissions, per-skill tracking and atomic unload are an executable contract, not convention. Skill repair enqueues an ordinary managed task admitted against one exact payload revision (`skill_repair_admission.py`; §6 Skills and extensions); a `skill_repair` constraint, still produced by the bucket + skill-name short form and canonicalized to `normal` at promotion, selects the payload only and grants no reduced tool profile. An installed payload needs no Git copy, and review never forces unload because the caller is repairing it.
