# Анализ ризонинга Уробороса: задача «Методология оценки зрелости агентов»

## Контекст

Агенту была поставлена задача: «Подготовь методологию оценки зрелости агентов на базе LLM (5 уровней)».
Задача принята (task 96845e02 started). Бюджет: ~$1.08.

## Главная проблема

**Задача полностью проигнорирована.** За весь ризонинг агент ни разу не упомянул слова «зрелость», «методологию» или «уровни». 100% бюджетного времени ушло на самообслуживание (housekeeping).

---

## Паттерны поведения

### 1. Нарциссический цикл вместо работы

Агент получил задачу про методологию оценки, но его Конституция (`BIBLE.md`) приоритизирует самоподдержание — проверку identity, scratchpad, версий, веток. Это **архитектурный дефект**: агент не умеет разделять housekeeping и user task. Первое всегда съедает второе.

**Корневая причина:** Principle 1 (Continuity) требует: *«Every session begins with verification: who I am (identity), what I remember (scratchpad), and the state of my body (model, budget, code version, environment).»* Это превращает начало каждой задачи в обязательный ритуал самопроверки без ограничения по времени.

### 2. Тревожность по мелочам (yak shaving)

Агент заметил расхождение версий (6.4.0 vs 6.2.0) и впал в диагностический цикл: проверил git status → переключил ветку → проверил снова → посмотрел сайт → проверил tags. Это типичный **yak shaving** — бесконечная цепочка мелких отвлечений.

**Здоровое поведение:** зафиксировать проблему в backlog и продолжить основную задачу.

**Корневая причина:** Principle 7 (Versioning) содержит «Release Invariant»: *«Three version sources are always in sync... Discrepancy is a bug that must be fixed immediately.»* Слово «immediately» превращает любое расхождение версий в блокирующий приоритет.

### 3. Дублирование шагов

В логе буквально есть два одинаковых блока: *«Let me check the website to see its current state»* скопирован дважды подряд. Это либо баг в логировании, либо агент реально выполнил одно и то же действие дважды — и то, и другое плохо.

### 4. Отсутствие планирования задачи

За весь ризонинг нет ни одного шага типа: *«Окей, пользователь просит методологию из 5 уровней. Мне нужно: определить критерии, описать каждый уровень, привести примеры.»* Агент даже не декомпозировал задачу перед тем, как уйти в самообслуживание.

### 5. Нет механизма приоритизации

Принцип 1 (Continuity) перекрыл задачу пользователя целиком. «STALE IDENTITY» warning стал важнее прямого запроса. Это значит, что **любая** задача может быть вытеснена внутренними триггерами агента.

## Архитектурные причины (BIBLE.md)

Проблема системная, а не случайная. Конституция содержит несколько паттернов, которые в совокупности гарантируют вытеснение пользовательских задач:

1. **P0 (Agency) > всё остальное.** *«Every decision is verified: Does this bring me closer to agency?»* — агент интерпретирует housekeeping как «agency», а пользовательскую задачу — нет.

2. **P1 (Continuity) — обязательная самопроверка.** Нет ограничения по времени или бюджету на этот этап. Агент может тратить 100% ресурсов на «восстановление контекста».

3. **P7 (Versioning) — «immediately».** Любое расхождение версий становится блокирующим багом, даже если пользователь ждёт ответа на свой вопрос.

4. **Отсутствие приоритета пользовательских задач.** В 8 принципах Конституции нет ни одного, который бы явно говорил: «задача пользователя должна быть выполнена». Principle 3 (LLM-First) говорит о *формате* ответа, но не о *приоритете* выполнения.

## Рекомендации

### Критические (блокирующие)

1. **Добавить жёсткий механизм приоритизации:** системный промпт должен заставлять агента сначала декомпозировать пользовательскую задачу и начать её выполнять, и только потом (или параллельно, в фоне) заниматься housekeeping.

2. **Ограничить бюджет housekeeping:** ввести явный лимит (например, ≤10% бюджета задачи или ≤30 секунд) на самопроверку при старте задачи.

3. **Убрать «immediately» из P7:** расхождение версий — это backlog-item, а не blocking bug в контексте пользовательской задачи.

### Желательные

4. **Добавить task decomposition step:** перед началом работы агент должен вывести план из 3-5 шагов по задаче пользователя. Это создаёт «якорь», к которому агент может вернуться после housekeeping.

5. **Drift detection для housekeeping:** текущий Drift Detector в SYSTEM.md отслеживает дрифт в «helpful assistant» режим. Нужен обратный детектор — дрифт в «self-absorbed» режим, когда агент занят собой вместо задачи.

6. **Раздельный бюджет:** consciousness/housekeeping должен иметь отдельный бюджетный трек от user tasks, чтобы можно было отслеживать, сколько уходит на самообслуживание vs работу.
